# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Hearts of Iron IV companion web app for planning campaigns, starting with a national focus tree planner (research is there too; production, divisions, navy, etc. may come later). It is a client-side Vue 3 + TypeScript + Vite single-page app with no backend.

## Commands

- `npm run dev`: start the Vite dev server (the app is served under `/hoi4-companion/`)
- `npm run build`: run `vue-tsc` type-check and `vite build` in parallel, writing to `dist/`
- `npm run test`: run Vitest once (`npx vitest run src/domain/__tests__/focusPlan.test.ts -t "name"` for a single file or test)
- `npm run type-check`: type-check only (`vue-tsc --build`)
- `npm run lint`: ESLint with `--fix` (flat config in `eslint.config.ts`)
- `npm run format`: Prettier on `src/` (no semicolons, single quotes, print width 100)

Tests live in `__tests__/` folders, which `tsconfig.app.json` excludes from type-checking.

## Deployment

Every push triggers `.github/workflows/main.yml`, which runs `npm install` and `npm run build`. Pushes to `main` also deploy `dist/` to GitHub Pages. That is why `vite.config.ts` sets `base: '/hoi4-companion/'`. Keep that base path when changing routing or asset URLs.

## Architecture

**No game data is committed or hosted.** The app reads focus trees from the user's own Hearts of Iron IV install, in their browser, and caches the parsed result in IndexedDB. Never add extracted game files or data to the repo. `HOI4_DIR="/path/to/Hearts of Iron IV" npm run test` also runs a test against a real install (skipped otherwise).

- Game logic is plain TypeScript with no Vue or DOM imports, so it is testable in Node. Keep it in `src/domain/`. Components only render it. Its subfolders are the architecture: `plan/` holds the planners (the focus planner depends on nothing but `focus.ts`, the research planner on nothing but `research.ts`; neither knows anything about game files), `campaign/` is the whole picture built from the plans (`industryAt` in `campaign/industry.ts`: factories, building slots and consumer goods on a date; `countryStateAt` in `campaign/countryState.ts`: the active ideas, stat totals, popularity, ruling party, leader and research environment of the country at a date; future planners add their inputs here), `parsers/` reads game script, `effects/` turns a focus's reward into display lines, and the files left at the top (`focus.ts`, `research.ts` (the shared research types), `production.ts` (the shared production types), `stats.ts`, `gameFiles.ts`, `gameImport.ts`, `definitions.ts`, `names.ts`, `focusEffects.ts`) are the shared types and the importer that drives the rest. Tests for all of it stay in `src/domain/__tests__/`, one file per area (`paradoxScript`, `focusTree`, `localisation`, `focusEffects`, `ideas`, `stats`, ...). `START_ID` (in `focus.ts`) is the `focusId` of what the starting state added.
- Import pipeline:
  - `parsers/paradoxScript.ts` is a generic parser for Paradox script. It keeps duplicate keys and order. The other files in `parsers/` each read one kind of definition out of it, and are used only by `gameImport.ts`.
  - `parsers/focusTree.ts` extracts `Focus` objects from a `common/national_focus` file. Cost is in weeks, converted to days. Each `prerequisite = { ... }` block is an OR group, and multiple blocks are ANDed.
  - `parsers/localisation.ts` reads `.yml` names.
  - `gameImport.ts` ties these together, in phases: parse the tree, read the definitions its
    effects refer to, read the countries and events it mentions, load localisation, then put
    names and stat definitions onto the effect lines (`nameLines.ts`; `effects/modifierLines.ts` lists the stats of ideas, relation modifiers and leader traits beneath the lines applying them). The start lines and leader candidates go through every phase as lists of lines of their own. Its helpers live in `gameFiles.ts` (the
    `GameFiles` interface of `readText`/`listFiles`, and `GAME_PATHS`), `definitions.ts`
    (`readDefinitions`, `readCountryHistory`) and `names.ts` (loading localised text).
  - **Research import:** `parsers/technologies.ts` (`readTechnologies`) reads every file of `common/technologies`, the folders from `common/technology_tags` (a folder's `available` picks the DLC variant by `ownedDlc`: BBA air, MtG navy, legacy armour; doctrine folders are left out) and `NTechnology` from `common/defines/00_defines.lua` (by regex, with fallbacks). `@variables` in positions (`y = @1936`) are defined per file, in the `technologies` block, and resolved in file order. A tech lists the techs it leads to, so its parents are found by turning those around. **All parents together are one OR group** (any one opens the tech: the tank and cruiser lines lead to each other, so AND would deadlock), a `dependencies` entry is a group of its own (AND), and `XOR` gives `exclusiveWith`. A tech can sit in several folders (`Technology.folders`). **A folder is several trees:** a tech's `position` is relative to the grid box of its tree in `interface/countrytechtreeview.gui` (`gridboxtype` named `<root tech>_tree` inside the folder's window, in 70px slots). `placeInTrees` assigns each tech to the first tree whose root leads to it and stores absolute slot coordinates; a box with `format = "LEFT"` (the army folders) runs sideways, so the tech's `y` (its year) becomes the column, and the folder is marked `sideways` for the connectors. `researchable` is false for special projects, `allow = { always = no }` and techs with no available folder (sub-technologies have none). Names come from localisation, falling back to the name of the first equipment the tech unlocks, then the id; stats are plain numbers only (`statBlocks.ts`). `ImportedCountry.research` (`ResearchData`) is the same for every country but cached with each. The start techs are `set_technology` lines in `countryStart.ts` (`research.kind = 'unlock'`, also inside top-level `has_dlc` branches).
  - **Production import:** `parsers/states.ts` (`readProduction`) reads the states the country owns at the start from `history/states` (`parseStateHistory`: the `owner` at the top level of `history`, so dated and `if` blocks are ignored; state-level `buildings` only, not `<province> = { naval_base }`; a cheap `owner = TAG` regex check before parsing), `common/state_category` (`local_building_slots`), the `shares_slots = yes` buildings of `common/buildings` and the `NProduction` consumer goods minimums from the defines (regex, with fallbacks). `ImportedCountry.production` (`ProductionData`, types in `production.ts`) is cached with each country; state names come from `STATE_<id>` localisation.
  - **Default laws:** history files do not set laws; the `default = yes` idea of each `law = yes` category (`parsers/laws.ts`, categories merged by name across `common/ideas` files) applies. `gameImport.ts` adds an `add_ideas` start line for each category whose ideas the history does not add (`defaultLawLines`), so they go through the idea/modifier passes and show as spirits (and `consumer_goods_expected_value` reaches `modifierTotals`). `ImportedCountry.laws` maps every law idea to its category (`lawCategoryOf`), passed on as `options.laws`, so adding a law in a reward removes the active law of the same category.
  - `focusEffects.ts` is a barrel over `src/domain/effects/`, whose header documents the whole
    effect pipeline in the order it runs. Inside: `lines.ts` (flattening, plus `opensBlock` /
    `blockEnd` / `childrenOf` / `outdent`, which every pass uses instead of hand-rolled index
    arithmetic), `collapse.ts`, `passes.ts`, `conditions.ts`, `format.ts`, `ideaLines.ts` and
    `statKeys.ts`.
- `src/import/` holds the browser-only pieces: `gameFolder.ts` implements `GameFiles` using `showDirectoryPicker` (Chromium, reads lazily) or `<input webkitdirectory>` (other browsers, which list every file in the install), and `cache.ts` is the IndexedDB cache.
- **Effect display.** Hovering a card (`FocusTreeGraph.vue`) shows the description (`<id>_desc` localisation), prerequisites and the flattened `completion_reward` (`Focus.effects`); the plan shows the same lines. `EffectList.vue` draws both and colours good/bad changes. Effects are humanized script lines, not translated to in-game wording, with reward values resolved to localised names. The pipeline is documented in the header of `focusEffects.ts`; the wording of each effect lives in `effects/format.ts` (`FORMATTERS`, dispatched on the effect name; a formatter that returns null falls through to the generic `<key>: <value>`) and `effects/collapse.ts` (`COLLAPSERS`: header key to a one-line replacement, mostly built by the `aboutSubject` / `namedBy` factories), and the tests show examples. To add a compound effect, add a collapser; for a one-word effect, `LABELLED_EFFECTS` in `format.ts`.
  - **Definitions read by id:** ideas (`parsers/ideas.ts`: the country's `ideasFile` first, then other `common/ideas` files only for ids still missing, with a plain `includes` check before parsing; only the `modifier` and `rule` blocks, not `targeted_modifier`), opinion modifiers, static modifiers (relation modifiers) and leader traits (`parsers/statBlocks.ts`: plain non-zero numbers only; corps commander traits are not read). Their stats are listed beneath the line that applies them (`effects/modifierLines.ts`), reversed for removals (`reverseModifier`). `readDefinitions` is the shared helper and `findBlocks` in `paradoxScript.ts` the layout-independent lookup.
  - **Stats** go through one pipeline in `stats.ts`: a `StatDefinition` (label, kind percent/number/flag, decimals, goodWhen) resolved from, in priority order, `src/data/statOverrides.ts` (extend this when a stat displays wrong), the game's `documentation/modifiers_documentation.md` (decimals and booleans only, not percent vs number), then a guess (`_factor` keys and fractional values are percent). Labels come from `MODIFIER_<KEY>` / `modifier_<key>` localisation, falling back to the humanized key. `defaultGoodWhen` sets the tone by key before the overrides (`*_cost_factor` better lower, building construction speeds better higher). Plain `key = number` effects (`STAT_EFFECT_KEYS`) also use this pipeline, so their labels live in `statOverrides.ts`.
  - **Names:** a country is named after its ruling party at game start, from `history/countries/<TAG> - *.txt` (`SOV_communism` is "Soviet Union", plain `SOV` is "Russia"). A state scope `46 = { ... }` is named from `STATE_46`. Texts built from other texts (`$KEY$`) are filled in after loading, and an idea with `name = X` is named from `X` (`parseIdeaNames`). `cleanLocalisation` strips colour codes and turns `[SCOPE.GetName]` into the scope tag. A `country_event` shows the title from its definition (`parsers/events.ts`, trying the file named like the id prefix first), with `From`/`Root` in the raw text (`parseLocalisation`'s `raw` map) filled in by `resolveEventText`; the faction name comes from the receiving country's `create_faction_from_template`.
  - **Left out on purpose:** the flag effects (`set_country_flag`, `set_state_flag`, `clr_country_flag`), array effects and `log`, `division_template` blocks (the focus tooltip already describes the unit), and any block left empty by that (`pruneEmptyBlocks`; a `limit` is not an effect). Everything inside `hidden_effect` is marked `hidden` and drawn grey and italic under a `Hidden effect:` header.
  - **Conditions:** `foldConditions` (run after names are resolved) folds a `limit` into the header it belongs to (`if`, `else_if`, `every_other_country`) as an English `condition`, and records the readable ones as data in `EffectLine.check`; a limit holding anything else stays raw. An `if` with an empty limit (the game files comment the DLC check out) always applies, so its `else` branches are dropped and the body is shown.
  - **DLC branches:** `resolveDlcConditions` resolves `has_dlc` for the DLCs in `src/data/dlc.ts` (`ownedDlc`: the player owns Man the Guns, By Blood Alone and Death or Dishonor); the branch that applies replaces the `if`. **The player does not own Arms Against Tyranny yet, so MIO rewards show their `else` branch (a designer idea), and this is expected to change**: flip the flag in `dlc.ts`, but MIO effects such as `mio:<id> = { add_mio_funds }` are not formatted yet, so that branch needs display work first.
  - Every path the importer reads is listed once in `GAME_PATHS` in `gameFiles.ts`; the non-Chromium folder fallback derives its filter from it (`READ_PATH_PREFIXES`), so add a directory there and it is readable in every browser.
- `src/domain/plan/focusPlan.ts` has `schedulePlan`, which schedules an ordered list of focus ids back to back, at `days / (1 + speedBonus)` each. It reports prerequisite, exclusivity and duplicate problems per focus, and still schedules invalid focuses.
- `src/domain/plan/focusSelection.ts` drives selection: `pathTo` returns the focuses to append so a clicked focus becomes valid (missing prerequisites first, cheapest option for OR groups, null if blocked by exclusivity). `removeWithDependents` drops a focus plus anything that loses its prerequisites. `isValidPlan` gates reordering. The UI therefore keeps the plan valid at all times, while `schedulePlan` still reports rule violations as a safety net.
- `src/domain/plan/researchPlan.ts` has `scheduleResearch(queue, techs, env, options)`, a pure function of the queue (`ResearchItem[]`: a tech id and the optional focus bonus chosen for it), the techs and a `ResearchEnvironment` (dated start techs, research slots, research speed, `set_technology` grants and `add_tech_bonus` bonuses, all from the campaign). It runs day by day: each free slot (lowest first) takes the first queued tech whose prerequisites are done and that no queued tech excludes, so a tech waiting for a prerequisite does not hold up the ones behind it. A slot adds `(1 + speed + bonus) / (BASE_TECH_COST * cost * (1 + penalty * max(0, yearsAhead - bonus.ahead)))` a day (years ahead counted from that day to Jan 1 of `start_year`), done at 1, in whole days. A bonus is spent when the tech starts, and only if it matches (a category or a tech id, told apart by `targetKinds`), was granted by then and has uses left; otherwise the row gets `bonus-unavailable`. `aheadOfTime` is the one place the penalty is worked out (years early, years a bonus ignores, cost factor); each `ScheduledResearch.ahead` holds it for the day the tech started, which the queue rows show, and the folder graph marks cards that would be early if added when the earliest research slot is free (`earliestFreeSlot`: amber bar; it ignores gaps where a slot waits on a prerequisite and what the new tech itself needs first) with the factor in the tooltip. The factor is a linear `1 + penalty x years` recomputed every day, which has not been checked against the game. A tech the country already has (start or granted) gets `already-researched` and no slot. Queued techs that never run are `unscheduled` with a reason. `availableBonuses` fills a row's dropdown. `plan/researchSelection.ts` mirrors `focusSelection.ts` (`pathToTech`, `removeWithDependents`, `isValidResearchPlan`, with the start techs as `known`).
- `src/domain/campaign/industry.ts` has `industryAt(production, state, techTotals)`: factories per type (start states plus instant focus builds; non-instant builds are listed as queued and not counted), building slots per state (`floor(categorySlots * (1 + global_building_slots_factor))`, the factor from ideas and technologies) plus the focuses' extra slots, and consumer goods. Focus builds come as `CountryState.construction` (`ConstructionBatch[]`, recorded in reward order by `recordBatches` in `applyReward.ts`: one per header block, with the numbered `state`, the `prefer` states, `random`, buildings, extra `slots` and resources; the country-wide totals stay as they were). `placeBatches` puts them into the state rows in order: a numbered scope in its state (unplaced if the country does not own it); a `random_owned_*` block in the first preferred state where, after its extra slots, the free shared slots (queued builds reserve slots) hold its shared-slot buildings, else the fitting state with most free slots (lowest id on ties), else the one with most free slots, those two marked `guessed`. Slots are those of the viewed date, while the game decides with the slots of the completion date. Only instant builds count in a row (`fromFocuses` notes what was placed); queued ones are listed in `queued` with their state, and `unplaced` holds what fits no state. **The consumer goods formula (`consumerGoodsFor`: `consumer_goods_expected_value * (1 + consumer_goods_factor)` of civ + mil factories, rounded up, with the define minimums, capped at the civs) is not verified against the game**; fix it in that one function after comparing with the production screen.
- `src/domain/plan/focusLayout.ts` resolves each focus's `x`/`y` (relative to `relative_position_id` when set) into absolute grid positions. `FocusTreeGraph.vue` draws the tree from them: absolutely positioned cards over an SVG of connector lines (px-per-grid-unit constants are at its top). Clicking a card toggles it in the plan; blocked cards are disabled. Game icons are deliberately not shown (copyrighted DDS art).
- The IndexedDB cache is versioned (`CACHE_VERSION` in `cache.ts`). Bump it when the `Focus`, `ResearchData` or `ProductionData` shape changes, which makes users re-import.
- `src/data/countries.ts` is the country selector list (only Romania so far). Each entry names its focus tree file.
- **Starting state:** `parsers/countryStart.ts` reads the 1936 part of `history/countries/<TAG> - *.txt` (starting `add_ideas`, `set_stability`/`set_war_support`/`set_research_slots`, `set_politics`, `set_popularities`, `set_technology` as an unlock line; not characters, OOBs or dated `1939.1.1` blocks) as effect lines, with stats turned into the additive keys (`add_stability`, ...) and popularities into `add_popularity` fractions. A top-level `if = { limit = { has_dlc = X } }` follows `ownedDlc` (unlisted DLCs count as not owned, so the Death or Dishonor king idea is absent until it is added to `dlc.ts`). `importCountryFocuses` returns `{ focuses, start, leaders, research }` (`ImportedCountry`); the start lines ride through the same name/modifier/stat passes as lines of their own and are cached with the focuses. `ImportTarget` needs the country `tag`. The starting leader is a `promote_character` line the importer adds (`parsers/leaders.ts`): the first `recruit_character` in the history whose `common/characters/<TAG>.txt` `country_leader` ideology belongs to the ruling party (sub-ideology to group via `common/ideologies`). `CountryState.leader` is `{ name, ideology, traits }` (traits listed beneath a `create_country_leader`/`add_country_leader_role` count as the leader's, not as one-off stat changes, and their stats are summed into the modifier totals); the overview shows it in its own Leader section.
- **`countryStateAt`** (`domain/campaign/countryState.ts`, which only runs the rewards in order and totals them; `applyReward.ts` is what one reward does, as a list of handlers over a `Working` state, so a new kind of effect is a new handler; `rewardScopes.ts` sorts a reward's lines into certain and conditional; `types.ts` has the shapes) applies the rewards of the focuses completed by a date. With `options.start`/`startDate` the start lines are applied first as a step with id `START_ID`, so stat totals and popularity are absolute (start plus plan).
  - **Research events:** `campaign/researchEvents.ts` records, as each reward is applied, the slots (the `add_research_slot` total, which includes the start), the research speed (`research_speed_factor` of the ideas and leader traits, also at each timed idea's expiry), `set_technology` grants (the start's become `startTechs`) and `add_tech_bonus` bonuses (numbered per focus in the order they happen, `BonusRef = { focusId, index }`). `CountryState.research` is that environment, so `countryStateAt(schedule, finish)` gives the whole timeline. `campaign/research.ts` has `planResearch`, which settles `has_tech` and the schedule together: pass one leaves `has_tech` unanswered, each later pass answers it (`options.hasTech(id, date)`, from the previous schedule's `researchedBy`) until the schedule stops changing, at most 3 passes. `researchStatusAt` is what the overview's Research section shows.
  - **What counts:** top-level lines and those inside `hidden_effect` or the country's own scope. `if`/`else`/`random_*`/`every_*` blocks are only listed (`conditional`), except that `add_resource`, `add_building_construction` and building slots are always collected: top-level, inside a `random_owned_*state` block (which picks one of the country's own states), and inside a numbered state scope `46 = { ... }` (assumed to be the country's own for now, so add an escape hatch if that turns out wrong). Those are summed per type, with instant builds counted apart. Other countries' scopes, state scopes and other countries' characters are skipped. Ideas are added, removed or (`add_timed_idea`) expire, and their modifiers are summed; a leader's traits are the leader's, not one-off stat changes, and their stats are summed into the modifier totals.
  - **Conditions:** `resolveConditions` (`campaign/conditions.ts`) settles each `EffectLine.check` against what the campaign knows when the focus completes: ideas active, focuses completed earlier in the plan, the ruling party so far, popularity once the start has set it, and who leads. It uses the state before the focus's own effects, so a popularity change and an `if` on it in the same reward see the old value. Evaluation is three-valued (`evaluateCheck`: true, false or undefined; one decisive term settles an `all`/`any` beside an unknown one). The branch that applies replaces the whole chain and counts like any other lines; a chain that cannot be settled stays from its first unanswered branch on (a leading `else_if` becomes an `if`) and is listed as conditional. `has_tech` is answered from `options.hasTech` (the research schedule, see above; without it the branch stays conditional). Not answered yet: other countries' state (factions, wars, their leaders).
  - **Leaders:** `has_country_leader = { id = N }` / `{ character = X }` is answered from `identity` (`create_country_leader` carries its `id` as `EffectLine.leaderId`; `promote_character` and `add_country_leader_role` give a character; it is unknown again after `retire_country_leader`, since the game picks the next leader). A character never matches a legacy id, so in a 1936 start `id = 550` (Carol II, only created in the `1939.1.1` block) is false. The game picking a new leader is modelled from `ImportedCountry.leaders` (`LeaderData`: the recruited characters with a `country_leader` role, in order, as named `promote_character` lines grouped by ideology group, plus the sub-ideology to group map; passed on as `options.leaders`): when a reward retires the leader, or changes the ruling party to one the leader does not lead for, and does not make a leader itself, the leader becomes the first candidate of the ruling party who has not been retired. `CountryState.leader` is `{ name, ideology, traits }`, and the overview shows it in its own Leader section.
- `src/stores/campaign.ts` (`useCampaign()`) is the one shared campaign: country, imported focuses and research data, plan, research queue (`researchPlan`, saved too; kept when still valid, cleared when the country changes), start date, speed bonus, the overview's `viewDate`, import status, and `production` and the computed `industry` (`industryAt` at the viewed date), `researchSchedule` / `researchEnvironment` / `researchStatus` (via `planResearch`, whose `hasTech` the overview's `state` uses). It is a module-level singleton, so every page shares it. `researchTotals` is what the technologies the country has on the viewed date add up to (`techModifierTotals` in `campaign/research.ts`: the plain stats of the start techs, focus grants and finished research, summed); the overview shows it as Modifiers from technology. `planEnd` is the end of the whole plan (the later of the last focus and the last research); the overview's date slider runs to it, and a view sitting at the end follows it. The plan and settings are saved to localStorage (`hoi4-companion:campaign`); focuses stay in the IndexedDB cache. A saved plan is kept when the focuses load and still valid, and cleared when the country changes.
- Routes (`src/router/index.ts`, hash history so reloads work on GitHub Pages): `/` is `views/OverviewView.vue` (date scrubber, government, national spirits, summed modifiers; `components/overview/`) and `/focus` is `views/FocusPlanView.vue` wrapping `components/focus/FocusPlanner.vue` (the plan: a list grouped under completion-year banners, showing each focus's dates and completion effects; focuses are added and removed only through the graph). `/research` is `views/ResearchPlanView.vue` wrapping `components/research/ResearchPlanner.vue` (the queue: a list in queue order under completion-year banners, with each row's dates, slot, days, issues, a bonus dropdown from `availableBonuses`, and move up/down gated by `isValidResearchPlan`) and `ResearchFolderGraph.vue` (folder tabs, cards on the folder grid with SVG connectors; click toggles through `pathToTech` / `removeWithDependents`; the tooltip lists the stats). `/production` is `views/ProductionView.vue` (the date scrubber shared with the overview, tiles for civ/mil/dock factories, consumer goods, available civs and slots, and a states table with a From focuses column, and lists of unplaced and queued builds). `App.vue` has the header, country selector and nav, and keeps pages alive (`KeepAlive`) so switching keeps scroll and state; each view needs a single root element for that. A plan row's end date opens the overview on that date (`completionDay`). `components/GameDataImport.vue` is the folder picker.
- The `@` alias points to `src/`.
