# Planners (`src/domain/plan/`)

- `src/domain/plan/focusPlan.ts` has `schedulePlan`, which schedules an ordered list of focus ids back to back, at `days / (1 + speedBonus)` each. `PlanOptions.loadedDays` (the store passes 1) takes that many days off the first focus only: checked in game, a 35-day first focus started on 1 Jan 1936 ends on 4 Feb, and the ones after it start with nothing done (assumed, not checked). It reports prerequisite, exclusivity and duplicate problems per focus, and still schedules invalid focuses.
- **Focus `available` and `bypass`:** `parsers/focusTree.ts` reads both triggers into `Focus.available` / `Focus.bypass` as `Check`s, only when they hold a term the campaign can answer (popularity, stability, government, focuses, ...; a trigger of only unknown terms is dropped, so it never blocks). `campaign/availability.ts` asks `available` of the country on the day the focus would start (`focusConditions`; unknown counts as available): `blockedByAvailability` adds the focuses (with the prerequisites they need first) that fail to the blocked cards, `unavailableInPlan` finds planned focuses that no longer pass, and the store's `toggleFocus` (`planning.ts`) refuses a blocked focus and, after a removal, drops planned focuses that became unavailable. `Focus.availableText` is the `available` block in English (the lines go through the name pass like a political option's, `availableLines` is dropped after); the focus tooltip says why a card is greyed out: `availabilityBlocks` (focus, start day, its `availableText`) or the planned focus that excludes it. A focus whose `bypass` holds as it starts gives no reward (`CountryState.bypassed`, shown on the plan row); assumed to still count as done, and its duration is unchanged.
- `src/domain/plan/focusSelection.ts` drives selection: `pathTo` returns the focuses to append so a clicked focus becomes valid (missing prerequisites first, cheapest option for OR groups, null if blocked by exclusivity). `removeWithDependents` drops a focus plus anything that loses its prerequisites. `isValidPlan` gates reordering. The UI therefore keeps the plan valid at all times, while `schedulePlan` still reports rule violations as a safety net.
- `src/domain/plan/researchPlan.ts` has `scheduleResearch(queue, techs, env, options)`, a pure function of the queue (`ResearchItem[]`: a tech id and the optional focus bonus chosen for it), the techs and a `ResearchEnvironment` (dated start techs, research slots, research speed, `set_technology` grants and `add_tech_bonus` bonuses, all from the campaign). It runs day by day: each free slot (lowest first) takes the first queued tech whose prerequisites are done and that no queued tech excludes, so a tech waiting for a prerequisite does not hold up the ones behind it. A slot adds `(1 + speed + bonus) / (BASE_TECH_COST * cost * (1 + penalty * max(0, yearsAhead - bonus.ahead)))` a day (years ahead counted from that day to Jan 1 of `start_year`), done at 1, in whole days. A bonus is spent when the tech starts, and only if it matches (a category or a tech id, told apart by `targetKinds`), was granted by then and has uses left; otherwise the row gets `bonus-unavailable`. `aheadOfTime` is the one place the penalty is worked out (years early, years a bonus ignores, cost factor); each `ScheduledResearch.ahead` holds it for the day the tech started, which the queue rows show, and the folder graph marks cards that would be early if added when the earliest research slot is free (`earliestFreeSlot`: amber bar; it ignores gaps where a slot waits on a prerequisite and what the new tech itself needs first) with the factor in the tooltip. The factor is a linear `1 + penalty x years` recomputed every day; checked in game at the 1936 start: the first day's progress is applied when research starts and the tooltip shows the days left after it, so Basic Machine Tools (1 + 157 days) and Construction II (1937, 1 + 374) match the planner exactly, and Construction III (1939, 1 + 871) is a day off. **Opening slots:** like the first focus, a tech that starts on the first day has a day of progress done (`ResearchOptions.loadedDays`, the store passes `FIRST_TECH_LOADED_DAYS` = 1; a tech that starts later gets none; the plain scheduler default is 0). Seen in game on Finland (Basic Machine Tools 5 June), assumed for every opening slot. **Techs that speed research up:** a tech's own `research_speed_factor` (Electronic Mechanical Engineering: +3%) is added to the speed from the day the tech is had (finished, start or granted), inside `scheduleResearch` (`techSpeedOn`); checked in game on Finland: Basic Machine Tools finished 5 June, not 8 June, once the +3% tech had finished mid-research (the planner had only the Export Focus's +5%; the in-game speed read 8%). A tech the country already has (start or granted) gets `already-researched` and no slot. Queued techs that never run are `unscheduled` with a reason. `availableBonuses` fills a row's dropdown. **Bonuses mid-research (assumed, to check in game):** a bonus granted on a day (`bonus.date`) is applied at once to the running techs it matches that have no bonus yet, in slot order, until its uses run out (`ScheduledResearch.bonusApplied`, shown as "bonus from <date>"), before free slots take new techs; unknown: whether the game also uses a bonus automatically on a tech that starts, and which tech gets it when two matching techs run at once. **Design teams:** `ResearchItem.designTeam` (a MIO id, saved with the queue, unknown ids dropped on load) adds `designTeamBonus + mio.researchBonus` to a slot's daily rate when one of the tech's categories is in the MIO's `researchCategories`; otherwise the row gets `design-team-mismatch`, `design-team-busy` (a MIO is the team of one research at a time) or `design-team-unavailable` (its `available` is false on the start day, answered by `ResearchEnvironment.mioAvailable`, built in `campaign/research.ts` from `countryStateAt`; unknown counts as available) and the tech runs without it. `ResearchSchedule.designTeams` lists the `{ mio, start, end }` intervals; the timeline says "with <MIO>". `ResearchEnvironment.categorySpeed` (a designer's `research_bonus` per category, dated like `speed`) is summed for the tech's categories into a slot's daily rate (`categoryBonusAt`). `plan/researchSelection.ts` mirrors `focusSelection.ts` (`pathToTech`, `removeWithDependents`, `isValidResearchPlan`, with the start techs as `known`).
- `src/domain/plan/politicsPlan.ts` (depends on `politics.ts` only): `dailyGain` and `purchaseCost` (`<slot>_cost_factor`, plus `<army|navy|air>_advisor_cost_factor` for an advisor's ledger) and the queue edits (`addPurchase`, `movePurchase`, `removePurchase`, `setNotBefore`, `knownPurchases`; no dependencies between items, so every order is valid). The gain a day is `(BASE_POLITICAL_POWER_INCREASE + political_power_gain) x (1 + political_power_factor + stability factor) - political_power_cost - focus cost - design team cost x teams in use`, and the balance starts at the first day's net gain (checked in game: Romania shows 2 on 1 January and 1 once the first focus is picked, Finland 1 and then 0, which is its 1.798 gross and 0.798 net). **Design teams:** `planPolitics` takes `designTeams` (`{ start, end }` intervals, the previous pass's research schedule in `planCampaign`; the first pass has none) and subtracts `PoliticsDefines.designTeamCost` (0.1) a day for each team in use from the day its research starts until it ends, with those dates as change points so `balanceAt` stays exact; `PoliticsSchedule.designTeamsAt` feeds the overview line "Design teams: -0.1 x n" (not checked in game). **Checked in game (Romania, 1 Jan 1936):** base 2, a +3% stability line in the tooltip (69% stability: `stabilityFactor` scales the good modifier's +10% from 50% to 100%, so +3.8%; the bad one's -20% from 50% down to 0%), and -1 a day for the running national focus (`gain_focus`; a focus is taken to be always running). **Confirmed in game:** PP ticks once a day, and Romania on 1 Jan 1936 (69.00% stability) gains 1.076 a tick with a focus running, as the model says (displays truncate; the wiki confirms the stability bonus is linear from 50% and only shown rounded down); Partial Mobilization becomes affordable on 20 May 1936. **Not checked yet:** whether `political_power_factor` also multiplies `political_power_gain`. Costs checked in game: economy and trade laws 150 flat, mobilization laws 150 for every rank moved (their `level`, `PoliticalOption.level`; `purchaseCost` takes the law it replaces, found with `replacedBy`), political advisors 150, military staff 100, concerns 150 (rounded to whole PP). `CountryState.stability` / `warSupport` are the actual values (`countryStat` in `campaign/totals.ts`: the start's `set_*` or 50% when the history sets none, plus changes, plus `<key>_factor` modifiers, plus for stability the ruling party's popularity x 0.15; war is not modelled); `has_stability` / `has_war_support` conditions use them too. `campaign/politics.ts` has `planPolitics`: the queue (`PoliticsItem`: `optionId`, `dismiss`, `notBefore`) is worked in order, event-driven on `countryStateAt`. At each change (a focus ends, a timed idea runs out, a purchase) it asks the state what is held, available and costs what, and buys the head of the queue the first day the balance covers it if that is before the next change (otherwise it looks again at the change, since a focus may make it available). The head waits for PP and the rest wait behind it; items that can never happen are `unscheduled` (`slots-full` for an advisor, `is-leader`, `not-recruited`, `unavailable`, `unaffordable`, `not-held`...), and an `available` the campaign cannot answer is allowed with an `availability-unknown` issue. **An option that is not available yet** is looked for in the days before the next change (`firstDayAvailable` in `campaign/politics.ts`: a week at a time, then the week it turns in day by day), since popularity and stability drift over a threshold with no event (Finland's Secure the Military, `fascism > 0.3`, is bought on 25 May, not at the next focus). A law or designer replaces the one in its slot, an advisor needs a free slot (dismiss first). The balance is the gain summed over time (capped at the define), plus `add_political_power` from the state's stat totals, minus what was spent (`balanceAt`, `gainAt`). **Decisions:** a decision is bought like an option with no slot: flat `cost` (`purchaseCost`, no cost factor), `available` answered, never held as an idea; its step is just the `complete_effect` lines (`purchaseEffects`). A `fireOnce` decision taken earlier in the queue is `already-taken`. The politics tab lists them in a Decisions group by category. Each purchase becomes a `Step` (id `politics:<index>`, `add_ideas` with the option's `slot`, `researchBonus` and modifier lines, or `remove_ideas`) in `PlannedPolitics.steps`.
- `src/domain/plan/constructionPlan.ts` has `scheduleConstruction(queue, production, env, options)`, a pure day-by-day scheduler like the research one. The queue is the user's `ConstructionItem`s (`building`, `state`, `levels`, built one level after another) then the focus-queued builds, which join the end on their focus's date. Each day the spare civs (civs minus `consumerGoodsFor`, from the factories built so far) go to the projects in queue order, up to 15 each; a project adds `civs x per-civ speed (4, or 5 when powered) x (1 + production_speed_buildings_factor + production_speed_<building>_factor) x infrastructure factor` a day to its level, done at the building's `base_cost` and built from the next day (a new civ joins, consumer goods rise). A level starts only with a free shared slot (a level in progress holds one) and room under `state_max`; one that waits gets `no-slots` and does not hold up the rest. Checked in game: a civilian factory queued on 1 January 1936 is done on 10 October in Muntenia (infrastructure 3: 6 spare civs x 5 (powered) x 0.8 x 1.6) and on 19 November in Bessarabia (infrastructure 2: x 1.4), so the linear infrastructure factor and the powered speed hold for Romania's start; state slots (city 6, rural 2) match too. **Three assumptions are checked only that far**, each one exported helper: `infraSpeedFactor` (`1 + effect * infra / 5`), `isPowered` (energy from base + coal against factories' scaled cost; unpowered drops the per-civ speed to 4) and `civCapPerProject` (the production line cap `MAX_CIV_FACTORIES_PER_LINE`, 15, which matches the game's construction cap). **Trade:** `ConstructionEnvironment.trade` is a list of `TradePoint`s (`received`, `importCost`, `coal`; built by `tradeOverTime` from the player's `TradeImport`s and `TradeReceived` entries, read off `tradeAt` like the factors). An import costs `ceil(amount x cic)` civs from its start to its end (`cic` is per resource in `common/resources`, 0.125 for all, read into `ProductionData.resourceCost`, fallback `DEFAULT_RESOURCE_COST`) and its coal adds to the energy; a received entry replaces the one before. The spare civs are `civs - consumer goods + received - importCost`, `isPowered` gets `coal + imported coal`, and civs received count `ENERGY_SCALE_PER_TRADE_FACTORY_EXPORT` (`ProductionDefines.energyScalePerTradeFactory`, 0.25) of a factory in the energy cost scaling. Exports are not modelled (the received civs do not say which resource left), so exporting coal does not lower the energy. Not checked in game. `industryAt` takes the trade of the date (`Industry.trade`, in `availableCivs`). `campaign/construction.ts` (`planConstruction`) builds the `ConstructionEnvironment` (`production.ts`): dated `factors` (modifier totals of the ideas and techs, sampled at each reward, timed idea expiry and research end, from `CountryState.snapshots` and the research schedule), `events` (instant builds, extra slots and resources per placed batch) and `focusBuilds` (non-instant builds in their placed state), placing the batches with the slots of the day the focus plan finishes.
- `src/domain/plan/focusLayout.ts` resolves each focus's `x`/`y` (relative to `relative_position_id` when set) into absolute grid positions. `FocusTreeGraph.vue` draws the tree from them: absolutely positioned cards over an SVG of connector lines (px-per-grid-unit constants are at its top). Clicking a card toggles it in the plan; blocked cards are disabled. Game icons are deliberately not shown (copyrighted DDS art).
